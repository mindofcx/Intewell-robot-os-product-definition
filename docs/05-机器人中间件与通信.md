# 机器人中间件与通信

> 文档状态：第一版草稿  
> 说明：本文介绍技术职责，不代表所有组件已在全部平台正式支持

## 1. 为什么机器人特别依赖通信

机器人是一个持续反馈的系统。相机、雷达、编码器、控制器和AI应用不断产生数据，多个计算任务需要在不同时间尺度上协同。

典型数据包括：

- 相机图像和点云等高带宽数据；
- 位姿、速度和力矩等周期控制数据；
- 任务、服务和状态等业务消息；
- 急停、碰撞和故障等安全信息；
- 日志、诊断和配置等管理数据。

这些数据不能简单采用同一种传输策略。机器人中间件需要根据数据的重要性、大小、频率和实时要求选择合适通道。

## 2. 中间件解决哪些问题

机器人中间件主要提供：

- 发布订阅、请求响应和任务Action等通信模型；
- 节点发现、连接管理和生命周期管理；
- 可靠性、优先级、缓存和QoS策略；
- 跨进程、跨系统、跨功能域和跨设备通信；
- 数据格式、接口和错误处理约定；
- 日志、数据记录、回放和通信诊断。

它的价值不是堆叠协议，而是让应用开发者使用相对一致的接口完成数据协同。

## 3. 常见通信技术

| 技术 | 主要特点 | 典型使用位置 |
| --- | --- | --- |
| DDS | 数据中心式发布订阅、QoS能力丰富、ROS2生态成熟 | ROS2节点、分布式应用和状态数据 |
| Zenoh | 面向数据、查询和发布订阅，关注跨网络与资源效率 | 跨设备、跨网络和统一数据空间探索 |
| 共享内存 | 同一计算平台内少复制、高带宽 | 虚拟机或进程间高频、大数据传输 |
| 虚拟网络 | 兼容标准网络协议和现有软件 | 虚拟机间通用网络通信 |
| RPC | 明确的请求与响应语义 | 配置、查询和控制服务 |
| EtherCAT / AUTBUS | 面向设备侧的周期通信 | 电机、驱动器、编码器和I/O |

### 能力状态

- **当前能力**：鸿道具备DDS、虚拟网络、共享内存和现场总线等技术基础，实际版本以软件BOM为准。
- **开发验证中**：不同通道组合、确定性增强和统一接口仍需按平台与场景验证。
- **演进构想**：探索以Zenoh等技术支持更统一的数据空间和跨网络协同。

## 4. 怎样选择通信方式

| 数据场景 | 首先关注 | 可考虑的通道 |
| --- | --- | --- |
| 同板大图像或点云 | 带宽、复制次数和CPU占用 | 共享内存 |
| 跨域状态与业务消息 | 接口兼容、可靠性和QoS | DDS或虚拟网络 |
| 配置与查询 | 请求结果和错误语义 | RPC或Service |
| 电机周期控制 | 周期、同步、最坏延迟 | EtherCAT、AUTBUS等现场总线 |
| 跨设备或跨网络协同 | 路由、发现和网络适应性 | DDS或Zenoh等方案 |

最终选择必须以测试结果为依据，而不是只比较协议名称。

## 5. 中间件与ROS2的关系

ROS2为机器人应用提供节点、Topic、Service和Action等开发模型。RMW层把ROS2接口映射到具体中间件实现，DDS是常见实现之一。

因此：

- ROS2更接近机器人应用框架和生态；
- DDS或Zenoh更接近数据通信实现；
- 共享内存和现场总线是更底层或更专用的传输通道；
- 鸿道操作系统提供这些组件运行所需的系统、隔离和设备基础。

## 6. 确定性不是一个协议就能保证

端到端确定性需要多个层次共同工作：

```mermaid
flowchart LR
    A[应用任务周期] --> B[中间件调度与QoS]
    B --> C[操作系统线程与中断调度]
    C --> D[跨域或网络传输]
    D --> E[现场总线周期]
    E --> F[驱动器与执行器]
```

只优化其中一层，不能自动保证整条链路。测试必须绑定具体硬件、系统版本、CPU分配、消息大小、频率、负载和统计口径。

## 7. 怎样证明通信能力可用

一项通信能力进入正式产品前，至少应提供：

- 可重复运行的发送与接收示例；
- 消息大小和频率覆盖说明；
- 时延、尾延迟、带宽和丢包结果；
- CPU和内存占用；
- 长时间稳定性和异常恢复结果；
- 测试环境、版本、配置和源数据说明。

现有Zenoh性能测试可作为研究和方案比较的证据，但单次环境下的结果不能直接转换为跨平台产品承诺。
