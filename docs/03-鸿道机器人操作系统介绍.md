# 鸿道机器人操作系统与三域融合架构

> 文档版本：v1.1_20260828
> 能力口径：具体支持范围以正式发布版本、软件BOM和测试报告为准

## 1. 产品定位

鸿道机器人操作系统是一套面向具身机器人的多域融合基础软件平台。它把操作系统、实时运行环境、虚拟化、设备适配、机器人中间件、开发工具和验证工具组织成一个可交付的平台，使智控、运控和通信主站等不同实时等级的任务能够独立运行、受控协同，并按硬件构型选择分离部署或融合部署。

这里的“操作系统”不是只指一个系统镜像。对机器人厂商而言，可用的平台还应包括启动和资源管理、BSP与驱动、跨域通信、SDK、调试工具、版本管理、兼容性矩阵和可重复的测试证据。

## 2. 为什么机器人需要多域融合

机器人同时处理三类性质不同的任务：

- **智控任务**：视觉、语音、定位、建图、规划、大模型和任务编排，通常需要Linux生态以及GPU/NPU等异构算力。
- **运控任务**：步态、平衡、轨迹、关节和力控制，关注固定周期、尾延迟、抖动以及异常时的安全降级。
- **设备通信任务**：连接驱动器、编码器、I/O和传感器，关注现场总线周期、时钟同步、报文完整性和故障恢复。

如果所有任务无差别地运行在同一个通用环境中，AI突发负载、内存回收、网络拥塞或驱动异常可能干扰控制闭环。如果永远拆成多个独立控制器，又会增加板卡、线束、功耗、协议转换和版本维护成本。

三域融合的目标不是简单地“把三个系统放到一块板上”，而是按照任务的实时等级、故障影响范围、资源需求和数据路径建立清晰边界，在边界内共享，在边界外隔离。

## 3. 整体分层

~~~mermaid

    APP[场景应用<br/>导航、抓取、巡检、交互]
    FW[机器人框架与组件<br/>ROS2、AGIROS、控制和感知组件]
    MW[机器人中间件<br/>数据、服务、QoS、发现、跨域通道]
    DOM[三域运行环境<br/>Linux / Linux RT / RTOS]

    BODY[传感器、驱动器、电机、关节和I/O]
    TOOL[SDK、Intewell Developer、QEMU、测试与交付工具]

    APP --> FW --> MW --> DOM --> HV --> BSP --> HW --> BODY
    TOOL -.开发、部署、诊断和验证.-> APP
    TOOL -.开发、部署、诊断和验证.-> DOM
~~~

各层职责不同：应用表达业务目标，机器人框架组织算法组件，中间件传递结构化数据和任务，操作系统提供进程与设备运行基础，Hypervisor提供多系统资源边界，BSP和驱动完成硬件适配。

## 4. 三个功能域分别做什么

### 4.1 智控域

智控域面向高算力和复杂软件生态，典型职责包括：

- 接入相机、激光雷达、语音和其他环境传感器；
- 运行视觉、语音、大模型和其他AI推理任务；
- 完成定位、建图、目标识别、场景理解和任务规划；
- 运行ROS2、AGIROS、导航、感知和人机交互组件；
- 向运控域发布目标位姿、轨迹约束或技能级任务，并接收反馈。

智控域通常使用Linux，以便复用AI框架、设备驱动、ROS2软件包和开发工具。它的实时性重点通常是任务级响应和数据新鲜度，而不是直接承担最短周期的关节闭环。

### 4.2 运控域

运控域把上层目标转换为连续、稳定、可执行的运动，典型职责包括：

- 步态、平衡、全身协调、轨迹和关节控制；
- 处理编码器、IMU、力传感器等反馈；
- 在固定周期内完成状态估计、控制计算和指令更新；
- 对通信超时、传感器异常和越界状态执行减速、停止或降级策略。

运控域可根据控制周期、算法复杂度和安全需求选择Linux RT或RTOS。评价重点是最坏情况下的调度延迟、控制抖动、上下文切换和故障响应，而不是单次平均执行时间。

### 4.3 通信主站域

通信主站域负责设备侧的确定性连接，典型职责包括：

- 运行EtherCAT、AUTBUS、CAN或其他现场总线主站能力；
- 管理驱动器、编码器、I/O和从站生命周期；
- 周期发送控制指令并采集设备状态；
- 进行时钟同步、链路监测、错误计数和从站恢复。

通信主站域通常采用RTOS或专用实时环境。它与机器人中间件并不是同一层：中间件承载应用和功能域之间的结构化数据，现场总线承载控制器与设备之间的周期报文。

## 5. Hypervisor在融合架构中的作用

Type-1 Hypervisor直接运行在硬件之上，为多个操作系统或运行环境提供可配置的资源边界。它需要处理：

| 资源或机制 | 需要回答的问题 |
| --- | --- |
| CPU与调度 | 哪些核由控制域独占，哪些核可以共享？高负载下是否会产生干扰？ |
| 内存 | 不同域的内存如何静态或受控分配？故障是否会越界？ |
| 中断与定时器 | 现场总线和控制中断是否能按预期送达？优先级如何配置？ |
| 设备分配 | PCIe、网口、USB、GPIO等设备由哪个域直接管理？ |
| 虚拟网络 | 域间通用数据如何传输，是否需要限速、隔离和监控？ |
| 共享内存 | 大图像、点云和状态数据如何减少复制并控制所有权？ |
| 生命周期 | 多个域如何启动、重启、升级和回滚？ |

融合不等于取消边界。适合共享的是数据和服务接口；需要隔离的是控制资源、设备所有权、故障处理和安全策略。

## 6. 可选部署构型

三域是逻辑职责，不是固定的硬件数量。平台可以根据整机需求采用以下构型：

| 构型 | 适用思路 | 需要重点验证的内容 |
| --- | --- | --- |
| 单域 | 早期原型、低复杂度设备或单一实时等级任务 | 系统调度、设备驱动和基础功能闭环 |
| 两域 | 智控与运控融合，或运控与通信主站融合 | 跨域链路、资源隔离和域间故障影响 |
| 三域融合 | 统一硬件承载高算力、实时控制和设备通信 | 最坏时延、CPU干扰、设备分配和安全降级 |
| 分布式多控制器 | 算力、功耗或安全要求不适合集中部署 | 网络尾延迟、时间同步、版本一致性和远程诊断 |

因此，架构评审不能只问“是不是三域”，还要记录每个域的所有者、运行环境、CPU和内存配额、设备归属、通信通道、刷新周期、故障策略和升级边界。

## 7. 一条任务如何经过三域

以“识别目标并完成抓取”为例：

1. 智控域从相机和其他传感器获得数据，完成目标识别和任务规划。
2. 智控域把目标位置、抓取姿态、速度约束和超时策略转换成结构化任务。
3. 运控域根据机器人当前状态生成身体、机械臂和关节的连续轨迹。
4. 通信主站域按总线周期将关节指令发送到驱动器，并采集编码器和力反馈。
5. 反馈数据沿相反方向回到运控域和智控域，系统根据误差继续修正。

每一条数据链路都应明确数据源、数据所有者、更新周期、有效期、传输通道、优先级、丢失处理和安全责任。只有把这些属性写进接口和测试用例，融合架构才具有可验证性。

## 8. 鸿道平台的能力组成

| 能力层 | 平台需要提供的能力 | 验收证据示例 |
| --- | --- | --- |
| 硬件与BSP | 启动、时钟、内存、网口、PCIe、USB、传感器和驱动适配 | 板卡支持矩阵、启动日志、驱动测试 |
| 虚拟化 | 多域启动、CPU/内存/设备分配、虚拟网络和共享内存 | 配置文件、资源隔离测试、故障注入结果 |
| OS运行时 | Linux、Linux RT、RTOS及其生命周期管理 | 版本清单、调度和恢复测试 |
| 机器人通信 | ROS2/RMW、DDS、共享内存、虚拟网络和现场总线衔接 | 接口示例、时延/带宽/丢包测试 |
| 开发交付 | SDK、Intewell Developer、编译、部署、调试、日志和诊断 | 工程模板、自动化脚本、问题定位记录 |
| 验证与维护 | QEMU早期验证、目标板回归、软件BOM和版本追踪 | 测试报告、兼容性矩阵、发布说明 |

QEMU适合接口验证、早期开发和自动化回归，但不能替代真实目标板上的现场总线、设备驱动、GPU/NPU、实时延迟、功耗和散热验证。

## 9. 实时性、隔离与安全边界

正式方案至少需要验证：

- 控制周期内的最大延迟、尾延迟和抖动；
- AI高负载、网络拥塞和日志写入时的跨域干扰；
- 共享内存和虚拟网络的带宽、队列深度及背压行为；
- 域重启、通信中断、设备掉线和异常恢复；
- 急停、限速、故障降级和人工接管路径；
- 版本升级、回滚、配置审计和软件供应链追踪。

“平均延迟很低”不能证明控制链路满足实时要求；“能够同时运行多个系统”也不能自动证明故障已经隔离。指标必须绑定硬件、系统版本、CPU分配、消息大小、频率、负载和统计方法。

## 10. 产品边界与能力状态

鸿道提供机器人应用的运行底座、资源隔离、通信基础和开发交付环境，但不等于机器人整机，也不替代所有上层算法。

| 鸿道平台通常提供 | 通常由整机或应用团队提供 |
| --- | --- |
| 操作系统、虚拟化、BSP和驱动基础 | 机械结构、关节选型和整机设计 |
| 实时运行环境、资源分区和生命周期 | 具体步态、抓取和业务算法 |
| 中间件、跨域通道和设备连接基础 | 针对场景训练的AI模型和数据集 |
| SDK、开发工具、调试和诊断能力 | 客户专属应用、工艺流程和运营系统 |
| 发布、测试和兼容性基础 | 最终整机安全设计与现场验收 |

- **当前基础**：操作系统、虚拟化、BSP、SDK和基础通信能力构成平台基础。
- **开发验证中**：两域、三域融合，以及CycloneDDS、Zenoh和共享内存的组合方案，需要在具体硬件和负载下持续验证。
- **演进构想**：把开发、运维和机器人任务的Agent能力纳入统一的权限、审计和技能调用体系。

正式支持范围以发布包、软件BOM、兼容性矩阵和测试报告为准。
