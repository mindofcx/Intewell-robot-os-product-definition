# 鸿道机器人中间件

> 文档版本：v1.1_20260828
> 能力口径：本文描述设计原则、技术选型和验证方法，不代表所有组件已在全部平台正式支持

## 1. 设计理念：按任务分层，而不是按协议堆叠

鸿道机器人中间件的核心设计理念，是按照任务的实时等级、数据规模、通信范围和故障责任划分不同层次，让每类任务使用最合适的传输机制。

机器人中的图像、点云、关节状态、控制指令、配置请求和安全事件，不能都采用同一种通信方式。中间件的职责不是把所有数据强行汇聚到一个协议，而是为应用提供统一的接口和可观测的策略，同时保留底层通道对实时性、带宽和隔离的控制能力。

因此，选型原则可以概括为：

1. **先定义数据契约**：明确数据所有者、更新周期、有效期、可靠性、优先级、顺序和安全等级。
2. **再选择传输层**：根据同机、跨域、跨设备或跨网络范围选择共享内存、DDS、Zenoh、RPC或现场总线。
3. **最后验证端到端行为**：以最坏延迟、尾延迟、抖动、丢包恢复、资源占用和故障降级作为验收依据。
4. **控制闭环优先保证确定性**：高频关节控制和急停链路不应因为上层消息系统的便利性而失去边界。

## 2. 分层架构

~~~mermaid
flowchart TB
    L5[任务与应用层<br/>导航、抓取、交互、Agent]
    L4[机器人框架层<br/>ROS2、AGIROS、控制组件]
    L3[功能域数据层<br/>Topic、Service、Action、事件]
    L2[跨域数据平面<br/>共享内存、虚拟网络、DDS、Zenoh]
    L1[设备实时层<br/>EtherCAT、AUTBUS、CAN、串行和I/O]
    L0[系统基础层<br/>Hypervisor、Linux RT、RTOS、时钟和安全]

    L5 --> L4 --> L3 --> L2 --> L1 --> L0
~~~

| 层次 | 主要任务 | 关注指标 | 可选机制 |
| --- | --- | --- | --- |
| 任务与应用层 | 表达目标、技能和业务流程 | 可用性、可追踪性、超时和权限 | Action、服务、任务状态机 |
| 机器人框架层 | 组织节点、算法和工具生态 | 接口兼容、生命周期和可复用性 | ROS2、AGIROS、导航和控制组件 |
| 功能域数据层 | 定义Topic、服务、Action和事件 | 数据契约、QoS、版本和状态 | ROS2接口、结构化事件、记录回放 |
| 跨域数据平面 | 连接进程、虚拟机、控制器和网络 | 尾延迟、带宽、发现、背压和资源隔离 | 共享内存、DDS、Zenoh、虚拟网络 |
| 设备实时层 | 连接驱动器、编码器和I/O | 周期、同步、抖动、错误计数和恢复 | EtherCAT、AUTBUS、CAN、专用驱动 |
| 系统基础层 | 提供资源、调度、时钟和安全边界 | 最坏调度延迟、隔离和故障影响 | Hypervisor、Linux RT、RTOS、硬件时间戳 |

这是一种职责分层，不要求每层对应一个独立进程或独立芯片。某些平台可以把多层组合在同一运行环境中，但接口边界、资源配额和测试责任仍应保留。

## 3. 按数据类型划分任务

| 数据类型 | 典型特征 | 推荐路径 | 设计要点 |
| --- | --- | --- | --- |
| 相机图像、点云 | 大数据、高带宽、允许一定丢帧 | 同机共享内存，跨机DDS或Zenoh | 零拷贝、缓冲池、背压和数据新鲜度 |
| 关节状态和控制目标 | 周期性、时序敏感、需要限时有效 | 运控域内实时通道，跨域使用受控数据通道 | 时间戳、有效期、优先级和超时降级 |
| 任务目标和导航Action | 低频、需要反馈和取消 | ROS2 Action或服务 | Goal、Feedback、Result、Cancel语义 |
| 配置、查询和诊断 | 请求响应、可审计 | RPC、Service或管理接口 | 身份、权限、错误码和重试上限 |
| 急停和安全事件 | 高优先级、需独立处理 | 硬件安全链路或专用实时通道 | 不依赖普通业务队列，不允许无界阻塞 |
| 记录、回放和遥测 | 大吞吐、可异步处理 | 数据记录服务、Zenoh订阅或文件通道 | 版本、时间基准、压缩和留存策略 |

中间件可以传递控制目标和状态，但不应默认承担最短周期的电机闭环。是否能进入控制链路，必须由实时预算、故障策略和测试报告决定。

## 4. ROS2、DDS与RMW的关系

ROS2提供节点、Topic、Service、Action、参数、生命周期、工具和软件包生态；RMW（ROS Middleware）是ROS2对底层通信实现的抽象层。DDS是ROS2中常见的实现路径，也可以通过其他RMW实现接入不同的数据传输技术。

这意味着：

- ROS2解决机器人应用如何组织和复用的问题；
- RMW隔离应用接口与具体通信实现；
- DDS提供数据中心式发布订阅、发现和QoS机制；
- 共享内存、虚拟网络、现场总线是更底层或更专用的通道；
- 鸿道负责为这些组件提供操作系统、虚拟化、设备和跨域运行基础。

ROS2的Topic、Service和Action不是简单的三种网络包，而是三种不同的应用交互语义。接口设计应同时定义消息类型、可靠性、历史深度、截止时间、生命周期和错误处理。

## 5. Dora与ROS2：互补关系

Dora（Dataflow-Oriented Robotic Architecture）将机器人和AI应用表达为有向数据流图：节点通过输入和输出连接，运行时负责数据流编排、节点生命周期和分布式执行。其公开仓库说明了多语言节点、YAML数据流、Apache Arrow数据表示、Zenoh通信、记录回放和监控等能力；其中性能数字属于其自身基准，不能直接推导为鸿道或其他平台的产品指标。

ROS2与Dora的关注点不同：

| 对比维度 | ROS2 | Dora |
| --- | --- | --- |
| 核心抽象 | 机器人节点、Topic、Service、Action和软件包 | 数据流图、节点、操作符和输入输出端口 |
| 主要价值 | 成熟的机器人生态、接口标准和工具链 | 用声明式数据流快速组合AI/机器人管线 |
| 通信抽象 | 通过RMW接入DDS等实现 | 以数据流运行时组织本机和分布式数据 |
| 语言和工程 | C++、Python及丰富ROS工具 | Rust运行时，并提供Python、C、C++等节点接口 |
| 实时表述 | 可配置QoS，但硬实时仍需专用控制设计 | 官方定位偏向低延迟和软实时，仍需场景验证 |
| 适合位置 | 机器人平台公共生态和长期接口 | 感知、AI编排、数据管线和快速实验 |
| 关系 | 可作为应用生态和设备接口 | 可通过桥接或适配与ROS2协同 |

对鸿道而言，Dora不必被看作ROS2的简单替代品。更实际的方式是：ROS2承担兼容性和机器人生态，Dora式数据流承担部分AI/感知管线编排；两者通过明确的消息转换、时间戳、QoS映射和故障边界协作。

## 6. CycloneDDS与Zenoh的验证方向

CycloneDDS是Eclipse基金会维护的开源DDS实现，支持OMG DDS和DDSI-RTPS相关规范，提供发现、发布订阅、QoS、可靠性和安全能力。其发现机制和QoS配置会受到网络拓扑、组播可用性、参与者数量和配置文件影响。

Zenoh面向数据、查询和发布订阅，强调把本地数据、边缘节点和网络资源放入统一的数据空间，并提供路由、查询、存储等能力。它适合探索跨设备、跨子网和边缘云协同，但具体机器人控制场景仍需验证其发现、路由、可靠性和资源开销。

两者不应只比较“谁更快”，而应按任务和部署边界比较：

| 维度 | CycloneDDS重点 | Zenoh重点 |
| --- | --- | --- |
| 生态兼容 | ROS2 RMW、DDS实体和QoS互操作 | 多语言API、数据空间和跨网络路由 |
| 发现 | DDS参与者和端点发现，组播或Peer配置 | 路由器/会话、局部发现和跨网络连接 |
| 数据模型 | Topic、类型、Reader/Writer和QoS | Key Expression、发布订阅、查询和存储 |
| 本机大数据 | 结合共享内存配置和具体实现验证 | Zenoh SHM或其他共享内存路径需单独验证 |
| 跨网络 | DDSI-RTPS、Peer、组播限制和安全配置 | 路由、查询、存储和网络拓扑适应性 |
| 主要风险 | 组播受限、发现规模、QoS匹配和配置复杂度 | ROS2生态映射、实时边界、路由器部署和语义转换 |

### 6.1 建议的A/B测试矩阵

固定同一硬件、内核、CPU亲和性、消息定义和负载，只替换通信实现：

| 测试组 | 负载和场景 | 记录指标 |
| --- | --- | --- |
| A | 同机小消息，单发布者/单订阅者 | p50/p99/max延迟、抖动、CPU和内存 |
| B | 同机大图像或点云，多订阅者 | 吞吐、复制次数、丢帧、队列深度 |
| C | 跨虚拟机或跨域 | 尾延迟、带宽、背压、域间干扰 |
| D | 跨设备、跨子网 | 发现时间、连接建立、重连和路由开销 |
| E | 丢包、重启、网络抖动 | 数据恢复、重复/乱序、超时和降级 |
| F | 高AI负载和日志压力 | 控制周期违约、资源争用和故障扩散 |
| G | ROS2接口兼容性 | Topic、Service、Action、QoS和工具兼容 |

每组至少记录消息大小、发送频率、样本数量、预热时间、统计方法、硬件型号、系统版本、配置文件和网络拓扑。结果应保存原始数据、脚本和环境说明，避免把单次演示结论写成平台承诺。

## 7. 鸿道中间件的工程原则

### 7.1 数据契约先于传输协议

每个接口至少定义：数据类型、生产者、消费者、频率、时间戳、有效期、可靠性、历史深度、优先级、错误码、版本兼容和安全等级。

### 7.2 控制面与数据面分离

节点启停、配置、健康检查和故障恢复属于控制面；图像、点云、状态和轨迹属于数据面。控制面应可诊断、可审计，数据面应可限流、可观测，两者不能相互无界阻塞。

### 7.3 本机、跨域、跨设备分别优化

同一地址空间或同一硬件上的大数据优先减少复制；跨虚拟机要控制共享内存所有权和安全边界；跨设备要显式处理发现、时间同步、网络故障和版本兼容。

### 7.4 以尾延迟和故障行为为验收重点

平均值只能说明常态。机器人产品还应观察最大延迟、p99/p999、抖动、超时、丢包恢复、重连、降级和长时间运行稳定性。

## 8. 能力状态与验收清单

- **当前基础**：鸿道具备操作系统、虚拟网络、共享内存、DDS和现场总线等技术基础，具体支持以软件BOM为准。
- **开发验证中**：CycloneDDS与Zenoh的组合、跨域数据平面、ROS2接口映射和确定性增强正在按平台测试。
- **演进构想**：形成统一的数据契约、通信策略编排、记录回放和跨域可观测性工具。

一项通信能力进入正式交付前，至少应有：

- 可重复运行的发布、订阅、服务和故障恢复示例；
- 消息大小、频率、节点数量和网络拓扑覆盖；
- 延迟、尾延迟、带宽、丢包、CPU和内存结果；
- 长时间稳定性、重启、断链和恢复结果；
- 版本、配置、硬件、测试脚本和原始数据归档。
