# 行业技术路线与代表产品

> 文档状态：第一版框架  
> 说明：第一版先梳理技术路线，后续再依据厂商官方资料补充具体产品

## 1. 为什么不直接做“友商排名”

机器人操作系统的名称相似，但产品边界可能完全不同。有的产品重点是Linux发行版，有的重点是ROS生态，有的提供实时控制，有的更接近仿真、开发工具或云平台。

直接比较功能数量容易产生误导。更合理的方法是先区分技术路线，再按照相同维度核对代表产品。

## 2. 常见技术路线

### ROS与开源生态路线

以ROS或ROS2为主要开发框架，强调软件包、算法、工具和社区生态。优势是开发资源丰富、上手快；产品化时仍需要处理硬件适配、实时性、安全、版本维护和交付支持。

### Linux与AI计算平台路线

以Linux、GPU/NPU和AI工具链为中心，强调感知、推理、仿真和模型部署。适合高算力智控任务，但运动控制和现场总线通常还需要实时系统或独立控制器配合。

### RTOS与实时控制路线

以RTOS、实时Linux、运动控制和工业总线为中心，强调周期、抖动、可靠性和设备连接。适合控制和通信任务，上层AI与机器人生态需要额外集成。

### 域控制器与虚拟化融合路线

通过Hypervisor在统一硬件上承载多个操作系统和不同实时等级任务，减少控制器数量并加强资源隔离。难点在于设备分配、跨域通信、性能验证和系统工程复杂度。

### AIOS与Agent原生路线

在传统系统之上增加面向Agent的任务、记忆、工具、权限和协作机制，让自然语言成为新的交互入口。这条路线仍处于快速发展阶段，在机器人中尤其需要处理实时性和物理安全边界。

## 3. 应该比较哪些维度

| 维度 | 核心问题 |
| --- | --- |
| 产品边界 | 是操作系统、框架、中间件、工具还是完整平台？ |
| 目标用户 | 服务算法开发者、控制工程师、整机厂还是最终用户？ |
| 运行环境 | 支持Linux、实时Linux、RTOS还是多系统？ |
| 实时能力 | 是否给出可复核的周期、抖动和负载条件？ |
| 隔离能力 | 是否支持多域、资源分区和故障隔离？ |
| 通信能力 | 支持哪些中间件、共享内存和现场总线？ |
| 机器人生态 | ROS2、控制、导航、仿真和工具支持到什么等级？ |
| AI与Agent | 支持模型部署、任务规划、工具调用还是Agent运行时？ |
| 开发闭环 | 是否支持创建、编译、部署、调试、诊断和恢复？ |
| 交付证据 | 是否提供版本、兼容性、文档、测试和支持策略？ |

## 5. 鸿道所处的路线

鸿道当前重点结合三条路线：

- 以工业OS和RTOS支撑实时控制与设备通信；
- 以Type-1 Hypervisor支撑多域隔离和融合部署；
- 以ROS、机器人中间件、SDK和开发工具支撑应用生态。

面向未来，鸿道将继续探索Agent智能运行层，让开发、运维和机器人任务能够通过统一、受控的Agent能力使用底层系统和机器人技能。

这不是简单追求组件数量，而是尝试把实时、隔离、通信、开发和智能任务组织成一套可交付的平台。
