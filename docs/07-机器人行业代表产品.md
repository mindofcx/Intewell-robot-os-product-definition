# 机器人行业代表产品调研：M-Robots、地瓜与智元

> 文档版本：v1.1_20260828
> 调研截止：2026-08-28
> 资料口径：本文优先采用厂商、开源社区、基金会和正式开发文档；公开资料未说明的内容标记为“待确认”

## 1. 调研范围与阅读方法

机器人行业中“机器人操作系统”可能指不同层次的产品：有的以通用系统和多机协同为核心，有的以边缘计算板卡加机器人软件栈为核心，有的以整机平台、运动控制中间件和具身智能数据闭环为核心。

本文将公开资料中的产品放在同一张能力地图中比较，但不把它们简单排名：

- **M-Robots OS**：以开源鸿蒙为底座，定位于分布式异构多机协同的机器人操作系统。
- **地瓜机器人 D-Robotics**：以RDK硬件、RDK OS和TogetheROS.Bot软件栈形成边缘机器人开发平台。
- **智元机器人 AGIBOT**：以整机产品、AimRT/ROS2开发接口、Link-U OS及数据和具身智能平台构成全栈体系。

公开宣传中的“实时”“全栈”“高性能”需要绑定硬件、版本、负载和测试方法理解，不能直接作为鸿道平台的对标指标。

## 2. M-Robots OS：分布式异构多机协同路线

### 2.1 公开定位

公开资料显示，M-Robots OS由深开鸿主导研发、依托开放原子开源基金会开源共建，基于开源鸿蒙构建，定位为分布式异构多机协同机器人操作系统。其目标是通过统一标准连接不同形态和不同厂商的机器人，降低软硬件适配和多机协同的重复工作。

资料中还提到M-Robots OS 1.0于2025年发布，后续进入开源社区治理和版本迭代。具体版本、组件清单和可下载代码应以项目仓库及正式发布说明为准。

### 2.2 技术路线解读

从公开定位可以推断，M-Robots OS重点解决的是“多设备、多形态和多机器人协作”的平台问题，而不只是单台机器人上的应用框架：

| 关注点 | 对机器人平台的含义 |
| --- | --- |
| 分布式异构 | 不同处理器、设备类型和机器人形态使用统一的系统与接口抽象 |
| 多机协同 | 机器人、传感器、边缘节点和环境设备能够进行任务联动 |
| 统一标准 | 通过公共接口减少厂商之间的适配和重复开发 |
| 开源共建 | 通过社区治理和公共代码形成可复用生态 |
| AI原生方向 | 将感知、决策和人机交互能力作为平台演进的一部分 |

需要注意：公开新闻中出现的极低时延、设备数量和AI能力描述属于发布材料中的产品主张。若要用于选型，仍需索取测试环境、统计口径、支持硬件、源代码版本和安全认证信息。

### 2.3 对鸿道的启示

M-Robots OS值得关注的不是“是否替代Linux或ROS2”，而是其平台边界：

1. 多机器人协同时，系统需要统一设备身份、能力描述、任务状态和数据模型。
2. 分布式系统需要处理发现、时间同步、断网自治、任务迁移和故障隔离。
3. 开源治理本身也是产品能力，必须配套版本、兼容性、贡献流程和安全响应。
4. “AI原生”仍应建立在可审计的权限、资源和安全边界上，不能把不确定的模型输出直接接入硬实时执行链路。

**待确认**：截至调研日，M-Robots OS具体支持的ROS2版本、DDS或Zenoh实现、实时内核、Hypervisor能力、主流芯片清单、性能测试报告和商业支持范围，公开资料尚未完整说明。

## 3. 地瓜机器人：RDK + TogetheROS.Bot边缘平台路线

### 3.1 产品边界

地瓜机器人（D-Robotics）公开文档将TogetheROS.Bot定义为面向机器人厂商和生态开发者的机器人操作系统，运行在RDK硬件上，并提供x86模拟器。RDK是面向智能计算和机器人应用的开发平台，覆盖X3、X5、S100、S600等系列；公开资料显示，部分型号通过BPU提供边缘AI算力，并通过异构设计兼顾感知推理和实时运动控制。

因此，TogetheROS.Bot更适合被理解为“与RDK硬件深度结合的机器人软件栈”，而不是脱离芯片、驱动和工具链的通用操作系统发行版。

### 3.2 软件栈特点

官方RDK文档说明，TogetheROS.Bot基于ROS 2 Foxy/Humble通信核心进行扩展和优化，并提供常用传感器、板载推理和视频编解码等组件。例如：

- 以hobot_sensor等组件减少常见机器人传感器的集成工作；
- 以hobot_dnn对接板载BPU，简化模型部署和推理调用；
- 以hobot_codec利用硬件能力完成视频编解码，降低CPU开销；
- 通过RDK OS系统镜像、TROS软件包和开发文档形成从烧录到运行的闭环；
- 通过x86模拟器和图像回放支持部分算法在上板前的验证。

地瓜还提供OpenExplorer算法工具链，支持PTQ、QAT和面向BPU的模型转换、量化与部署。对机器人厂商而言，这种“芯片 + OS镜像 + ROS2扩展 + AI工具链 + 示例”的组合可以缩短边缘感知应用落地时间。

### 3.3 适用场景与边界

| 适合发挥优势的场景 | 需要另外验证或补齐的内容 |
| --- | --- |
| 视觉感知、目标检测、VSLAM和移动机器人 | 高端全身控制、强安全等级和复杂多域隔离 |
| 基于RDK的低成本边缘AI原型 | 与非RDK硬件、其他BSP和异构加速器的迁移 |
| ROS2算法包快速部署和参考方案 | 现场总线主站、严格控制周期和跨控制器一致性 |
| 从开发板到参考机器人方案的快速迭代 | 大规模车队管理、产品认证和长期版本维护 |

TogetheROS.Bot的公开文档对ROS2扩展、硬件加速和开发流程说明较多，但对于不同版本的最坏时延、控制周期、域隔离和安全认证，仍需按具体产品和商业版本确认。

### 3.4 对鸿道的启示

地瓜路线说明，机器人平台的竞争力不仅在通信协议，还在于：

- 对目标芯片的BSP、驱动、AI编译器和硬件加速做深度整合；
- 为常见传感器、导航和视觉算法提供可运行的参考实现；
- 让开发者能通过模拟器、镜像、工具链和示例快速形成闭环；
- 把“可部署、可调试、可复现”作为平台交付的一部分。

鸿道如果面向多芯片、多OS和多域融合，应在保持硬件抽象的同时，建立类似的板卡支持矩阵、设备适配层、模型部署接口和验证流水线。

## 4. 智元机器人：整机、开放接口与具身智能平台路线

### 4.1 产品和平台组成

智元机器人（AGIBOT）公开产品体系包括远征、灵犀、精灵、酷拓、灵巧手和数据采集与训练平台。其官方站点同时列出灵渠 Link-U OS、灵心 LinkSoul、灵创 LinkCraft、Genie Studio、AimRT Framework和AGIBOT World等平台或开源项目。

这表明智元的“机器人操作系统”并不是单一安装包，而是由整机控制、开发接口、运动控制中间件、数据采集、模型训练和应用平台共同构成的产品体系。

### 4.2 灵犀X1与AimRT

智元官方资料将灵犀X1定位为全栈开源人形机器人，并提供硬件图纸、URDF、仿真、Sim2Sim、强化学习训练、推理和调试等资料。其配套开源工程说明，X1软件系统使用AimRT作为中间件，并包含平台驱动、模型推理和软件仿真模块。

从系统工程角度看，这种开放方式把以下接口暴露给开发者：

- 机械和执行器的结构、BOM及装配资料；
- 机器人模型和仿真接口；
- 运动控制、强化学习和模型推理工程；
- 中间件和平台驱动；
- 数据可视化、遥操作和调试工具。

官方X1页面还公开了关节模组、域控制器和通信能力等产品信息，例如域控制器提供Linux二次开发SDK，并面向执行器提供EtherCAT到多路FDCAN的转发和硬件同步能力。具体数量、频率和接口以对应版本资料为准。

### 4.3 ROS2开发接口与Link-U OS

智元X2 AimDK文档说明，其开发接口基于ROS2标准，支持C++和Python；官方中文站点将灵渠 Link-U OS列入平台体系。由此可以区分三种层次：

1. **整机与域控制**：关节、电机、传感器、域控制器和运动控制链路。
2. **机器人开发接口**：AimDK、ROS2接口、AimRT以及仿真和调试工具。
3. **上层平台与智能服务**：Link-U OS、数据服务、模型和技能生态。

公开资料对Link-U OS的内部内核、隔离机制、调度策略和通信实现披露有限，因此不能仅凭产品名称判断其与Linux、ROS2或中间件的边界。

### 4.4 对鸿道的启示

智元路线对鸿道的启示主要有四点：

- 把机器人平台接口做成可复用的SDK，而不是只交付整机内部代码；
- 将仿真、遥操作、数据采集、训练、推理和部署连接成连续闭环；
- 通过AimRT或ROS2接口降低算法开发者进入整机系统的门槛；
- 对外开放时，同时发布硬件版本、软件版本、依赖和可复现实验方法。

鸿道可以将这些能力映射到三域架构：智控域承载感知、数据和模型工具，运控域承载确定性的状态估计与控制，通信主站域承载设备周期和同步；中间件与SDK负责将三域接口以可验证方式暴露给开发者。

## 6. 对鸿道产品规划的建议

### 6.1 明确产品层次

公开材料中应清楚区分：

- 鸿道OS和Hypervisor提供什么；
- 鸿道机器人中间件提供什么；
- ROS2、Dora、AimRT等框架处于什么位置；
- 板卡BSP、现场总线和AI工具链由谁维护；
- 哪些是当前交付，哪些正在验证，哪些只是演进方向。

### 6.2 建立三类可验证资产

1. **平台资产**：版本化的系统镜像、BSP、驱动、Hypervisor配置和软件BOM。
2. **开发资产**：SDK、接口定义、ROS2适配、仿真环境、示例工程和调试工具。
3. **证据资产**：兼容性矩阵、时延/吞吐测试、故障注入、长稳和升级回滚报告。

### 6.3 形成差异化评价指标

不直接复制竞品宣传指标，建议以以下问题评价鸿道：

- 同一硬件能否按资源边界运行Linux、Linux RT和RTOS？
- 智控、运控和通信主站之间是否有明确的数据所有权和故障责任？
- CycloneDDS、Zenoh、共享内存和现场总线能否按任务选择并可观测？
- 开发者能否从创建工程、编译、部署、调试一直走到真实目标板验证？
- 出现高负载、断链、域重启或设备异常时，系统是否能按策略降级和恢复？
- 对不同芯片和板卡迁移时，哪些接口和测试可以复用？
